Since you are studying QEMU and already have a disk image, the next logical step is to actually **boot something**. 

Because you previously asked about creating a binary "without a compiler," the most educational way to proceed is to create a **minimal boot sector**. This allows you to see exactly how QEMU interacts with the "hardware" (BIOS/UEFI) and the disk without needing a full OS like Linux.

Here is the path forward for your study.

### 1. Create a "Dummy" Bootloader (The "No Compiler" way)
A computer's BIOS looks for a specific signature (`0x55AA`) at the very end of the first 512 bytes of a disk to decide if it is bootable. We can create a file that satisfies this requirement using `dd` (a standard utility available in your Nix shell).

Run this to create a 512-byte file filled with zeros, but ending with the boot signature:
```bash
# Create 510 bytes of zeros
dd if=/dev/zero of=boot.bin bs=512 count=1

# Write the magic boot signature (0x55 0xAA) to the last two bytes
printf '\x55\xAA' | dd of=boot.bin bs=1 seek=510 conv=notrunc
```
Now you have a `boot.bin` that is technically "bootable," though it does nothing but hang the CPU (because it contains no actual instructions).

### 2. Boot the Raw Binary in QEMU
Before using your `qcow2` disk, try booting this raw binary. This confirms your QEMU installation is working.

```bash
nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin
```
**What to expect:** A window will open. You will see "SeaBIOS" start up, and then it will likely say "No bootable device" or simply hang. This is successful—it means QEMU emulated the x86 BIOS, looked at your file, and tried to execute it.

### 3. Use your `test_disk.qcow2`
Now, let's integrate the disk image you created. To make your `qcow2` disk bootable, you have to "write" that bootloader into the disk image.

Since `qcow2` is a compressed format, you cannot use `dd` on the file directly. You have two choices:

**Option A: Use a Raw image (Easier for study)**
If you just want to study boot-sectors, create a raw image instead of qcow2:
```bash
qemu-img create -f raw test_disk.raw 512M
dd if=boot.bin of=test_disk.raw conv=notrunc
nix develop --command qemu-system-x86_64 -hda test_disk.raw
```

**Option B: Use the `qcow2` image (The "Real" way)**
To put data into a `qcow2` image from the outside, you typically use `qemu-img` to convert it or boot it and write from inside. However, for study purposes, you can tell QEMU to use your `test_disk.qcow2` as the primary hard drive:

```bash
nix develop --command qemu-system-x86_64 -hda test_disk.qcow2
```
*(Since the disk is currently empty/zeros, this will just show the BIOS error, which is the correct behavior).*

### Summary of the "Study" Workflow
If you want to continue this study, here is the suggested curriculum:

1.  **The BIOS Level:** Write a tiny assembly program (using `nasm`) that prints "Hello" to the screen, compile it to a `.bin`, and boot it with `-hda`.
2.  **The Kernel Level:** Instead of a bootloader, try booting a pre-compiled Linux kernel (`vmlinuz`) using the `-kernel` flag in QEMU.
3.  **The Disk Level:** Use `qemu-img` to create a disk, boot a Linux ISO (like Alpine Linux), install the OS onto that `qcow2` disk, and then try booting the disk alone.

**Pro Tip for Mac Users:** Since you are on Apple Silicon, `qemu-system-x86_64` is purely emulating. If you want to see a massive speed increase, you can study `qemu-system-aarch64`, which can use the Mac's native hardware acceleration via the `-accel hvf` flag.

The reason QEMU doesn't "quit" automatically is that your `boot.bin` contains essentially "nothing" (zeros). In CPU terms, zeros are often interpreted as `NOP` (No Operation) instructions. The CPU is simply looping infinitely at the very first byte of your file, so QEMU stays open waiting for the CPU to do something else.

In a CI (Continuous Integration) environment, this is a problem because the job will hang until it hits a global timeout.

Here are the three ways to handle this for CI, ranked from "Easiest/Best Practice" to "Hardest."

### 1. The CI Standard: The `timeout` command (Recommended)
Instead of trying to make QEMU "quit," you tell the operating system to kill the QEMU process after a few seconds. This is the standard way to test emulators in CI.

Run your command like this:
```bash
timeout 5s nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin -nographic
```
*   **How it works:** If QEMU is still running after 5 seconds, the `timeout` command sends a kill signal to QEMU and returns a non-zero exit code.
*   **CI Tip:** You can check the exit code in your CI script to determine if the boot "timed out" (failed) or finished.

### 2. The "Verification" approach (Better for Testing)
If your goal is to test that the file **actually loaded**, you don't want it to just hang. You want it to do something detectable, then stay in a loop.

To do this without a compiler, you can slightly modify your `boot.bin` to include a "Halt" instruction, but even then, QEMU usually stays open. Instead, you can write a tiny Assembly program using `nasm` that prints a character and then loops.

**Example (using `nasm`):**
1. Create a file called `boot.asm`:
   ```nasm
   mov ah, 0x0e    ; Teletype output
   mov al, 'A'     ; Print 'A'
   int 0x10        ; BIOS interrupt
   jmp $           ; Infinite loop (hang)
   ```
2. Compile and run:
   ```bash
   nasm -f bin boot.asm -o boot.bin
   nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin -nographic
   ```
3. **In CI:** You can pipe the output to a file and check if 'A' exists:
   ```bash
   nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin -nographic > output.txt
   # Use a timeout so it doesn't hang forever
   timeout 5s nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin -nographic > output.txt
   grep -q "A" output.txt && echo "Success" || echo "Fail"
   ```

### 3. The "Power Off" Instruction (The "Real" way)
To make QEMU actually shut down, the guest OS (your bootloader) must send a specific signal to the virtual hardware to "Power Off."

In the old BIOS standard, this is `INT 19h`. However, this is much harder to do with a "no compiler" approach because you have to manage registers perfectly.

### Summary for your CI script:
Use **Option 1**. It is the most robust and requires the least amount of changes to your current workflow.

**The final command for your CI config:**
```bash
timeout 5s nix develop --command qemu-system-x86_64 -drive format=raw,file=boot.bin -nographic
```
*(Note: If `timeout` isn't available in your specific CI environment, you can use `(qemu-command & sleep 5; kill $!)` as a workaround.)*

To redirect output in a CI environment, you have three ways to do it, depending on how "clean" you want the logs to be.

### 1. The Simple Way (Standard Redirection)
You can just append the standard redirection operators to your existing command. This will capture everything QEMU outputs to both `stdout` and `stderr`.

```bash
nix develop --command timeout 15s qemu-system-x86_64 -hda test_disk.qcow2 -nographic > output.log 2>&1
```
*   `>` redirects standard output (stdout).
*   `2>&1` tells the shell to send standard error (stderr) to the same place as stdout.

**The Problem:** Because you are using `nix develop`, the `output.log` will also contain "Nix noise" (e.g., *"Entering shell..."* or *"*nixpkgs* binaries being loaded...*"). This can make it hard to parse the log in CI.

---

### 2. The "Clean" Way (Isolating QEMU output)
If you want **only** the QEMU output in your log file and want to hide the Nix shell setup messages, wrap the command in a bash string:

```bash
nix develop --command bash -c 'timeout 15s qemu-system-x86_64 -hda test_disk.qcow2 -nographic > output.log 2>&1'
```
By putting the `>` inside the `bash -c` string, the redirection happens *after* Nix has finished setting up the environment, so your log file stays "pure."

---

### 3. The "Pro" Way (Adding a Test Script to your Flake)
Since you are already using a `flake.nix`, the most robust way to handle this for CI is to create a dedicated **test script** in the flake. This allows you to add "assertions" (e.g., checking if the log contains "SeaBIOS") so the CI actually passes or fails correctly.

Add this to your `flake.nix` under the `apps` section:

```nix
    apps.aarch64-linux.test-boot = {
      program = "test-boot";
      description = "Run QEMU and verify boot in CI";
      shell = {
        buildInputs = with nixpkgs.legacyPackages.aarch64-linux; [ qemu coreutils ];
      };
      text = ''
        echo "Running QEMU test..."
        # Run QEMU, capture output, and timeout after 15s
        timeout 15s qemu-system-x86_64 -hda test_disk.qcow2 -nographic > test_output.log 2>&1

        fi
      '';
    };
```

```bash

```

1.  **No Noise:** It encapsulates the logic so your CI runner only sees the final result (Success or Failure).

### 3. The "Intelligent" Way (Best Practice)
In CI, usually, you **do** want it to fail if QEMU crashes, but you might want to ignore the **timeout** (since a bootloader hanging is expected behavior).

You can do this by catching the specific exit code for a timeout (which is `124`).

```bash
nix develop --command bash -c 'timeout 15s qemu-system-x86_64 -hda test_disk.qcow2 -nographic -serial file:test.log; [ $? -eq 124 ] && echo "Timed out as expected" || true'
```
*   **How it works:** It runs the command. If the exit code is `124` (the standard code for `timeout`), it prints a message and moves on. If it's any other error (like a disk error), it still lets the error pass through (or you can add `|| true` to the very end to kill all errors).
